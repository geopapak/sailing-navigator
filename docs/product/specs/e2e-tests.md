## Στόχος

Ένα σύνολο αυτόματων tests που ανοίγει την πραγματική εφαρμογή σε browser (Chromium και WebKit σε μέγεθος iPhone, 375 και 320 px) και περνά τις βασικές ροές όπως ένας χρήστης: πρώτη χρήση, σύνδεση, αγώνας, προπόνηση, ενημέρωση έκδοσης, offline. Τρέχει σε κάθε push και PR στο GitHub και τοπικά στον υπολογιστή του `qa-tester`. Ωφελεί πρώτα τον skipper και το πλήρωμα, χωρίς να το βλέπουν. Σφάλματα όπως το καρουζέλ που ξαναβγαίνει (P-046) ή η ερώτηση θέσης σε κάθε ανανέωση (P-048) πιάνονται πριν φτάσουν στο κινητό τους, στο σπίτι ή στη μαρίνα. Ωφελεί και την ομάδα: κάθε φάση (Φ4, Φ5, P-049) αλλάζει οθόνες, και τα tests δείχνουν αμέσως αν χάλασε κάτι από τα παλιά. Δεν υπάρχει κανένα κόστος: GitHub Actions σε δημόσιο repo, κανένα AI, καμία κλήση σε server παραγωγής.

## Εκτός εύρους

- **Ποτέ** το live site (GitHub Pages), το staging (Cloudflare Pages), οι Workers παραγωγής/staging, πραγματικοί λογαριασμοί, κλειδιά ή secrets.
- **Ποτέ** κλήση AI με χρέωση. Τα `/analysis`, `/chat`, `/advice`, `/certificate`, `/entrylist` απαντούν μόνο από fixtures.
- Πραγματικά όργανα (Signal K / NMEA). Μόνο η πηγή «Προσομοίωση (για δοκιμή)» (`source: 'simulator'`).
- Πραγματικά πλακίδια χάρτη, πρόγνωση Open-Meteo, βυθομετρία EMODnet, ORC, AIS: κόβονται ή απαντούν από μικρά συνθετικά fixtures. Ο χάρτης (MapLibre/WebGL) στη v1 ελέγχεται μόνο ότι ανοίγει χωρίς σφάλμα, όχι τι σχεδιάζει.
- Visual regression (σύγκριση screenshots εικονοστοιχείο προς εικονοστοιχείο). Τα screenshots στη v1 είναι μόνο για διάγνωση. Ίσως αργότερα, μετά την P-049.
- Πραγματικό iPhone / iOS Safari ως εφαρμογή αρχικής οθόνης. Το WebKit του Playwright **δεν** είναι iOS. Η ενότητα «Τι δεν πιάνει το WebKit του Playwright» λέει τι μένει στον χειροκίνητο έλεγχο.
- Tests πάνω σε πραγματικό τοπικό server (`wrangler dev --local`). Αυτό είναι η **P-045b**, μετά τη v1.
- Tests φόρτου, ασφαλείας (υπάρχει ήδη `npm run pentest`), προσβασιμότητας με εργαλείο (π.χ. axe). Το τελευταίο ίσως σε επόμενο βήμα.
- Deploy από GitHub Action. Το deploy μένει όπως είναι (`pages.yml` για production, χειροκίνητα για staging).
- Αλλαγή στη λειτουργία της εφαρμογής. Ο developer προσθέτει μόνο `data-testid` και ένα build mode `e2e`.

## User stories

1. Ως **skipper** θέλω το καρουζέλ πρώτης χρήσης να μη ξαναβγαίνει και το κινητό να μη ρωτά για τη θέση σε κάθε άνοιγμα, ώστε στη μαρίνα και στο νερό η οθόνη να είναι αμέσως έτοιμη.
2. Ως **τακτικός** θέλω η ροή «Νέος αγώνας → εκκίνηση → Live → τερματισμός → Ιστορικό» να ελέγχεται πριν από κάθε έκδοση, ώστε να μη μου χαλάσει μέσα σε αγώνα.
3. Ως **μέλος πληρώματος** θέλω η προπόνηση (γύροι, παύση, σύνοψη, GPX/CSV) να δουλεύει μετά από κάθε αλλαγή, ώστε το debrief να έχει σωστά νούμερα.
4. Ως **skipper** θέλω μια νέα έκδοση να μην ξαναφορτώνει ποτέ την εφαρμογή μέσα σε έξοδο, ώστε να μη χάνεται ίχνος και χρόνος.
5. Ως **πλοηγός** θέλω η εφαρμογή να ανοίγει χωρίς ίντερνετ, με θέμα «Νύχτα» και «Πολύ μεγάλα» γράμματα σε μικρό κινητό, ώστε να τη διαβάζω τη νύχτα στο νερό.
6. Ως **διαχειριστής** (ιδιοκτήτης) θέλω να βλέπω σε κάθε push/PR αν πέρασαν τα tests και, αν όχι, screenshot και trace, ώστε να αποφασίζω αν θα κάνω deploy.
7. Ως **διαχειριστής** θέλω τα tests να μην αγγίζουν ποτέ production, κλειδιά ή AI με χρέωση, ώστε να μην υπάρχει ρίσκο ούτε κόστος.
8. Ως **qa-tester** θέλω να τρέχω τα ίδια tests τοπικά με μία εντολή και να βλέπω τον browser όταν θέλω, ώστε να γράφω νέα tests γρήγορα.

### Build για τα tests

- Νέο script `build:e2e` = `vite build --mode e2e`. Το `.env.e2e` ορίζει `VITE_SERVER_URL=https://api.e2e.example.test`. Το `.test` είναι δεσμευμένο TLD και δεν βγάζει ποτέ σε πραγματικό host. Έτσι, ακόμα κι αν ξεφύγει ένα αίτημα από τα fixtures, δεν φτάνει πουθενά.
- Σημαντικό: σήμερα το `DEFAULT_SERVER` (`src/ui/settings.ts`) πέφτει στον Worker **παραγωγής** όταν λείπει το `VITE_SERVER_URL`. Στο CI δεν υπάρχει `.env.local`, άρα ένα απλό `npm run build` θα έδειχνε σε production. Γι' αυτό τα tests τρέχουν **μόνο** πάνω στο `build:e2e`. Το Vite διαβάζει το `.env.e2e` πριν από το `.env.local`, άρα ένα τοπικό `.env.local` δεν το αλλάζει.
- Τα tests τρέχουν πάνω στο build (`vite preview` ή `e2e/serve.mjs`), όχι στο `vite dev`. Έτσι ελέγχονται ο πραγματικός service worker και το CSP.

### Ψεύτικος server και φύλαξη δικτύου

- Ο `server.ts` απαντά στο `https://api.e2e.example.test/*` με σταθερές JSON απαντήσεις: `/config`, `/health`, `/auth/register`, `/auth/login`, `/auth/logout`, `/auth/forgot`, `/me`, `/me/terms`, `/me/export`, `DELETE /me`, `/sync`, `/notes/crew`, `/crews*`, `/invites/*`, `/analysis`, `/chat`, `/advice`, `/windy`, `/certificate`, `/entrylist`, `/orc/boat`, `/ais`. Οι τύποι απαντήσεων εισάγονται από το `src/sync/api.ts` (`PublicUser`, `SyncItem`) ώστε ένα fixture που ξεφεύγει από το συμβόλαιο να σπάει στο `tsc`.
- Τα μηνύματα σφάλματος των fixtures είναι τα ίδια με του `server/accounts.ts`, π.χ. «Λάθος email ή κωδικός.» (401), «Υπάρχει ήδη λογαριασμός με αυτό το email.» (409), «Πολλές λάθος προσπάθειες. Δοκίμασε ξανά σε 15 λεπτά.» (429).
- Ο server μετρά τις κλήσεις ανά διαδρομή (`server.calls('/analysis')`), για κριτήρια όπως «ακριβώς μία κλήση AI».
- Ο `network-guard.ts` επιτρέπει μόνο το origin της εφαρμογής (`http://localhost:4173`) και το `https://api.e2e.example.test`. Τα `tiles.openfreemap.org`, `tiles.openseamap.org`, `*.emodnet-bathymetry.eu` και `*.open-meteo.com` απαντούν από fixture ή κόβονται (`route.abort()`). **Οποιοδήποτε άλλο** αίτημα, και ειδικά κάθε `*.workers.dev`, `*.github.io` ή `*.pages.dev`, κάνει το test να αποτύχει με μήνυμα «Αίτημα εκτός λίστας: <host>».
- Χωρίς service worker (ροές 1–4): `serviceWorkers: 'block'` και `page.route`, ίδιο σε Chromium και WebKit.
- Με service worker (ροές 5–6), σε Chromium **και** WebKit: όταν τη σελίδα ελέγχει service worker, το `page.route` / `context.route` δεν βλέπει με σιγουριά τα αιτήματα. Ο Playwright εγγυάται routing αιτημάτων μέσα από service worker μόνο στο Chromium. Γι' αυτό οι ροές 5–6 **δεν** στηρίζονται στο routing. Οι ίδιες απαντήσεις των fixtures σερβίρονται από έναν μικρό τοπικό ψεύτικο server, το `e2e/fake-server.mjs` στο `http://127.0.0.1:8788`, που ξαναχρησιμοποιεί τους handlers του `server.ts`. Το build `build:e2e-sw` έχει `VITE_SERVER_URL=http://127.0.0.1:8788` (από `.env.e2e-sw`· το CSP ήδη επιτρέπει `http://127.0.0.1:*`). Τα εξωτερικά hosts (πλακίδια, Open-Meteo) δεν χρειάζονται στις ροές 5–6. Αν ξεφύγει αίτημα προς αυτά, απλώς αποτυγχάνει (στο CI ως offline), και ο ψεύτικος server γράφει ποια hosts ζητήθηκαν, ώστε το test να ελέγχει ότι δεν ζητήθηκε τίποτα άλλο. Ο ψεύτικος server ακούει **μόνο** στο `127.0.0.1` και αρνείται κάθε άλλο `Host`.
- Πρώτη δουλειά του `qa-tester` (spike ½ μέρας): να επιβεβαιώσει ότι στο WebKit του Playwright (Linux στο CI, Windows τοπικά) γράφεται και ενεργοποιείται service worker, ότι το `setOffline(true)` + reload ανοίγει την εφαρμογή από την cache, και ότι η εναλλαγή A/B φέρνει νέο worker σε «waiting». Ό,τι δεν δουλεύει γράφεται στην παρακάτω λίστα με `test.fixme` και αιτία, όχι σιωπηλό skip.

### Θέση, χρόνος, όργανα

- Θέση: `context.setGeolocation({ latitude: 37.90, longitude: 23.66 })`. Η άδεια δίνεται με `grantPermissions(['geolocation'])` μόνο όπου το test το θέλει. Ένα `addInitScript` μετρά τις κλήσεις `navigator.geolocation.watchPosition` / `getCurrentPosition` (`window.__geoCalls`), γιατί ο Playwright δεν βλέπει το παράθυρο άδειας.
- Χρόνος: `page.clock` (ψεύτικο ρολόι). Ο αγώνας και η προπόνηση «περνούν» λεπτά σε δευτερόλεπτα, και η ώρα 02:00 της P-044b φτάνει χωρίς αναμονή. `timezoneId: 'Europe/Athens'`, `locale: 'el-GR'`.
- Όργανα: Ρυθμίσεις → «Όργανα σκάφους» → «Προσομοίωση (για δοκιμή)». Ο `Simulator` (`src/instruments/simulator.ts`) δίνει θέση, TWS/TWA/BSP κάθε 1″ και δύο «αντιπάλους» (`SIM ΑΣΤΑΡΤΗ`, `SIM ΝΗΡΕΑΣ`). Επειδή το Live παίρνει θέση από τα όργανα όταν είναι ζωντανά (`NavContext`), οι ροές 3–4 δεν χρειάζονται GPS κινητού.

### Τι δεν πιάνει το WebKit του Playwright, και πώς καλύπτεται

Το project `webkit-iphone` είναι η μηχανή WebKit με μέγεθος, touch και user agent iPhone. **Δεν είναι iOS Safari**: είναι άλλη έκδοση της μηχανής, σε Linux/Windows, χωρίς το λειτουργικό του iPhone. Πιάνει διαφορές CSS/JS της μηχανής (layout στα 320/375 px, Permissions API που λείπει, IndexedDB, service worker), αλλά όχι τα παρακάτω:

| Δεν ελέγχεται αυτόματα | Γιατί | Πώς καλύπτεται |
|---|---|---|
| Εφαρμογή αρχικής οθόνης (standalone PWA): ξεχωριστή αποθήκευση από το Safari, το iOS που ξαναρωτά για θέση (P-048) | δεν υπάρχει «Προσθήκη στην αρχική οθόνη» στον Playwright | χειροκίνητη λίστα iPhone στο staging, σε κάθε κυκλοφορία που αγγίζει πρώτη χρήση, θέση ή ενημέρωση |
| Το πραγματικό παράθυρο άδειας θέσης και η μνήμη της επιλογής του iOS | ο Playwright δίνει ή δεν δίνει την άδεια, δεν δείχνει παράθυρο | μετρητής `__geoCalls` (καμία κλήση = κανένα παράθυρο), συν η χειροκίνητη λίστα |
| Κύκλος ενημέρωσης service worker του iOS (ελέγχει κυρίως όταν ανοίγει η εφαρμογή, σταματά στο παρασκήνιο) | το WebKit του Playwright δεν «κοιμάται» και δεν κλείνει την εφαρμογή | οι κανόνες «ποτέ reload σε έξοδο» ελέγχονται εδώ· η ώρα που το iOS βλέπει τη νέα έκδοση ελέγχεται χειροκίνητα στο staging |
| Σβήσιμο αποθήκευσης από το iOS (π.χ. μετά από μέρες χωρίς χρήση) | δεν προσομοιώνεται | κριτήριο 13 (σβήσιμο μιας από τις δύο αποθηκεύσεις) και P-047 αν χρειαστεί |
| Κλειδωμένη οθόνη, wake lock, ήχος/φωνή ειδοποιήσεων, δόνηση | εξαρτώνται από συσκευή και λειτουργικό | χειροκίνητα, όπως σήμερα (P-013, P-023) |
| Πραγματικό GPS/κινητό δίκτυο, αργή σύνδεση στη θάλασσα | ο Playwright δίνει σταθερή θέση και ιδανικό δίκτυο | fixtures με καθυστέρηση (Ακραίες περιπτώσεις), πρόβα στο νερό |
| Notch / safe area, πραγματικά δάχτυλα με γάντια | οι εξομοιωτές δεν έχουν notch | χειροκίνητα σε iPhone |

Η χειροκίνητη λίστα iPhone (≤ 15′) τη γράφει ο `qa-tester` στο `docs/product/qa/iphone-checklist.md` και την τρέχει πριν από κάθε κυκλοφορία που αγγίζει αυτά τα σημεία.

## Κριτήρια αποδοχής

### Α. Υποδομή και ασφάλεια

1. Δεδομένου ότι ο `qa-tester` έχει κάνει `npm ci` και `npx playwright install --with-deps chromium webkit`, όταν τρέχει `npm run e2e`, τότε γίνεται `build:e2e`, σηκώνεται ο τοπικός server, τρέχουν όλα τα projects και στο τέλος βγαίνει αναφορά HTML στο `playwright-report/`.
2. Δεδομένου ότι ένα test προκαλεί αίτημα σε host εκτός λίστας, όταν γίνει το αίτημα, τότε το test αποτυγχάνει με «Αίτημα εκτός λίστας: <host>» και το αίτημα δεν φεύγει από τον υπολογιστή. Στις ροές 5–6 ο έλεγχος γίνεται έμμεσα: ο ψεύτικος server του `127.0.0.1:8788` πρέπει να έχει δεχτεί τα αναμενόμενα αιτήματα, και η λίστα αιτημάτων της σελίδας (`page.on('request')`, όσα φαίνονται) δεν έχει άλλο host.
3. Δεδομένου ότι τρέχει οποιοδήποτε test, όταν η εφαρμογή διαβάζει τον server της, τότε είναι το `https://api.e2e.example.test` (ροές 1–4) ή το `http://127.0.0.1:8788` (ροές 5–6). Ένα πρώτο «smoke» test ανά build το ελέγχει και, αν δει άλλο, σταματά όλη τη σειρά.
4. Δεδομένου ότι τρέχει όλη η σειρά, όταν τελειώσει, τότε ο server των fixtures έχει δεχτεί 0 αιτήματα σε διαδρομή AI που δεν ζήτησε ρητά κάποιο test, και κανένα αίτημα δεν έφυγε προς Anthropic ή άλλο host.
5. Δεδομένου ότι υπάρχουν τα αρχεία στο `e2e/fixtures/`, όταν τρέχει `npm test` (Vitest), τότε ένας έλεγχος αποτυγχάνει αν κάποιο αρχείο έχει email που δεν τελειώνει σε `@example.test`, κείμενο που μοιάζει με κλειδί (`sk-ant-`, `Bearer ` με πραγματικό μήκος token, `ghp_`) ή URL `workers.dev` / `github.io` / `pages.dev`.
6. Δεδομένου ότι γίνεται push σε οποιοδήποτε branch ή ανοίγει/ενημερώνεται PR, όταν δεν αφορά μόνο `docs/**`, `design/**` ή `**/*.md`, τότε τρέχει το workflow «E2E» (`.github/workflows/e2e.yml`) με `permissions: contents: read`, χωρίς κανένα `secrets.*`, με `on: pull_request` (όχι `pull_request_target`) και `concurrency` που ακυρώνει την προηγούμενη εκτέλεση του ίδιου branch.
7. Δεδομένου ότι το E2E αποτυγχάνει στη φάση «προειδοποίησης», όταν γίνει push στο `main`, τότε το «Deploy to GitHub Pages» τρέχει κανονικά. Το E2E φαίνεται κόκκινο στο commit/PR και γράφει στο job summary ποια tests απέτυχαν.
8. Δεδομένου ότι ένα test αποτυγχάνει στο CI, όταν τελειώσει το job, τότε ανεβαίνει artifact `e2e-report-<run>` με την αναφορά HTML, screenshot τη στιγμή της αποτυχίας και trace της επανάληψης, που μένει 7 ημέρες. Αν όλα περάσουν, ανεβαίνει μόνο η αναφορά HTML (χωρίς traces).
9. Δεδομένου ότι τρέχει το CI, όταν μετρηθεί ο χρόνος, τότε όλο το job (εγκατάσταση, build, tests) τελειώνει σε **≤ 10′**, και τα tests μόνα τους σε **≤ 5′**. Κάθε test έχει όριο 60″ (90″ για τις ροές 3 και 5). Ένα test που ξεπερνά το όριο μετρά ως αποτυχία.

### Β. Ροή 1: πρώτη χρήση (P-046, P-048)

10. Δεδομένου ότι ένας νέος χρήστης «Δοκιμαστής» (`crew@example.test`, χωρίς σκάφη, `/sync` χωρίς στοιχεία) συνδέεται σε καθαρό browser, όταν τελειώσει ο πρώτος συγχρονισμός, τότε φαίνεται το καρουζέλ με τίτλο «Καλώς ήρθες, Δοκιμαστής» και «Βήμα 1 από 5».

### Η. Αστάθεια (flaky) και πύλη deploy

57. Δεδομένου ότι ένα test αποτυγχάνει στο CI, όταν ξανατρέξει αυτόματα (`retries: 2` στο CI, `0` τοπικά) και περάσει, τότε η αναφορά το σημειώνει «flaky» και το job summary το γράφει σε χωριστή λίστα «Ασταθή».
58. Δεδομένου ότι ένα test βγει flaky 2 φορές μέσα σε μία εβδομάδα, όταν το δει ο `qa-tester`, τότε μέσα σε 1 εργάσιμη μέρα είτε το διορθώνει είτε το βάζει σε καραντίνα (`test.fixme` με σχόλιο `// flaky: P-045 <ημερομηνία> <αιτία>`) και ανοίγει γραμμή στο `docs/product/BACKLOG.md` ή issue. Τα tests σε καραντίνα δεν είναι πάνω από 3 ταυτόχρονα.
59. Δεδομένου ότι τα tests τρέχουν σε «προειδοποίηση», όταν περάσουν **2 εβδομάδες** από τη μέρα που η v1 μπήκε στο `main`, με όλες τις εκτελέσεις του `main` και των PR πράσινες εκτός από πραγματικά σφάλματα της εφαρμογής, και καμία νέα καραντίνα την τελευταία εβδομάδα, τότε ο `qa-tester` το αναφέρει στον PO, που καταγράφει στο `DECISIONS.md` την ενεργοποίηση της πύλης.
60. Δεδομένου ότι η πύλη είναι ενεργή (branch protection στο `main`: «Require a pull request before merging», υποχρεωτικό status check «E2E», «Require branches to be up to date», χωρίς απευθείας push, και χωρίς εξαίρεση για τον ιδιοκτήτη, ή με εξαίρεση μόνο για επείγουσα διόρθωση, δες Ανοιχτά ερωτήματα), όταν κάποιος προσπαθήσει `git push` απευθείας στο `main`, τότε το GitHub το αρνείται. Όταν ένα PR έχει κόκκινο «E2E», τότε το κουμπί «Merge» είναι ανενεργό.
61. Δεδομένου ότι ένα PR συγχωνεύεται με πράσινο «E2E», όταν ενημερωθεί το `main`, τότε το «Deploy to GitHub Pages» τρέχει όπως σήμερα. Το `pages.yml` δεν αλλάζει. Το `e2e.yml` τρέχει και στο push του `main`, για ενημέρωση.
62. Δεδομένου ότι το check λέγεται «E2E» στο branch protection, όταν αλλάξει όνομα το job ή το workflow, τότε ο `qa-tester` ενημερώνει τον ιδιοκτήτη πριν από το merge, γιατί αλλιώς το check που απαιτείται δεν τρέχει ποτέ και κάθε PR μένει κολλημένο.

## Δεδομένα & API

- **Καμία** νέα στήλη, migration D1, sync kind ή route στον Worker για τη v1.
- Νέα αρχεία (εργαλεία ανάπτυξης, όχι μέρος της εφαρμογής): `playwright.config.ts`, `e2e/**`, `.env.e2e`, `.github/workflows/e2e.yml`.
- `package.json`: devDependency `@playwright/test` (μόνο αυτό). Scripts:
  - `build:e2e` — `tsc --noEmit && vite build --mode e2e`
  - `e2e` — όλα τα projects, headless
  - `e2e:ui` — Playwright UI mode για γράψιμο/αποσφαλμάτωση
  - `e2e:headed` — μόνο `chromium-375`, με ορατό browser
  - `e2e:report` — `playwright show-report`
- `.gitignore`: `playwright-report/`, `test-results/`, `dist-e2e/`, `blob-report/`.
- Το Vitest (`vite.config.ts → test.include`) κοιτά μόνο `src/**/*.test.ts` και `server/**/*.test.ts`, άρα τα `e2e/*.spec.ts` δεν μπλέκονται. Ο έλεγχος fixtures του κριτηρίου 5 μπαίνει ως `src/e2eFixtures.test.ts` ή στο `server/`, ή προστίθεται `e2e/**/*.test.ts` στο include.

- Fixture σκάφους: πλήρες `BoatProfile` με scoring, φτιαγμένο από το υπάρχον προφίλ του repo (`src/boat/treIrene.ts`) με **άλλο όνομα, αριθμό πανιού και χωρίς αριθμό αναφοράς ORC** («Αστάρτη», `GRE-1234`, `orcRef` κενό). Χρησιμοποιείται μόνο για τον υπολογισμό στόχων και διορθωμένου χρόνου στα tests.
- Πρόγνωση: συνθετική, φτιαγμένη από κώδικα (σταθερός άνεμος), όχι αποθηκευμένη απάντηση του Open-Meteo.

## Ασφάλεια & ιδιωτικότητα

- **Χωρίς secrets** στο `e2e.yml`, ούτε `GITHUB_TOKEN` με δικαιώματα εγγραφής (`permissions: contents: read`). `pull_request`, όχι `pull_request_target`, ώστε PR από fork να μην πάρει τίποτα.
- Οι browsers δείχνουν μόνο σε `localhost`, `api.e2e.example.test` και (ροές 5–6) `127.0.0.1:8788`. Ο έλεγχος των κριτηρίων 2–3 είναι το βασικό φρένο. Το `.env.e2e` είναι το δεύτερο.
- **Τα artifacts του CI σε δημόσιο repo τα βλέπει κάθε συνδεδεμένος χρήστης του GitHub.** Τα traces περιέχουν όλα τα αιτήματα, το `localStorage` και την IndexedDB. Γι' αυτό μέσα μπαίνουν μόνο fixtures: χρήστης «Δοκιμαστής», `crew@example.test`, `new-crew@example.test`, token της μορφής `e2e-token-…`, σκάφος «Αστάρτη» `GRE-1234`, συντεταγμένες ανοιχτά του Φαλήρου. Κανένα πραγματικό όνομα, email, αριθμός δελτίου αθλητή ή ίχνος. Ο έλεγχος του κριτηρίου 5 το επιβάλλει.
- Ο ψεύτικος server των ροών 5–6 (`127.0.0.1:8788`) ακούει μόνο τοπικά, δεν έχει καμία σύνδεση με D1 ή Anthropic και σερβίρει μόνο τα fixtures.
- Branch protection (μετά τις 2 εβδομάδες): το ρυθμίζει **μόνο ο ιδιοκτήτης** στο GitHub (Settings → Branches / Rulesets). Κανένας agent δεν αλλάζει ρυθμίσεις του repo.
- Τοπικά: τα `.env.local` και `.dev.vars` του `qa-tester` δεν διαβάζονται από τα tests της v1. Στην P-045b (`wrangler dev --local`) χρησιμοποιείται χωριστό `--env e2e` με δικό του `.dev.vars.e2e` **χωρίς** `ANTHROPIC_API_KEY`, ώστε ένα τοπικό κλειδί να μη χρησιμοποιηθεί κατά λάθος. Ένα πρώτο test ελέγχει ότι το `/health` απαντά χωρίς ρυθμισμένο AI.
- GDPR: δεν υπάρχουν προσωπικά δεδομένα, άρα τίποτα για εξαγωγή ή διαγραφή. Η ροή εξαγωγής/διαγραφής λογαριασμού ελέγχεται ως λειτουργία (v1 με fixture, P-045b στον τοπικό server).
- Logs του CI: ο Playwright γράφει ονόματα tests και σφάλματα, όχι σώματα αιτημάτων. Τα fixtures δεν γράφουν στο console τα tokens.

1. Μία φορά: `npm ci` και `npx playwright install --with-deps chromium webkit` (στα Windows χωρίς `--with-deps`).

## Αλλαγή στη ροή εργασίας μετά την πύλη (πρόταση για το `WORKFLOW.md`, δεν έχει γίνει)

Τι αλλάζει στην πράξη:
- Σήμερα: τοπικό `git merge --no-ff` στο `main` και `git push` → deploy. Μετά: push του **branch** και Pull Request προς το `main`. Το merge γίνεται στο GitHub, μόνο με πράσινο «E2E» (και με το `npm test` που ήδη τρέχει). Το deploy ξεκινά από το merge, όπως σήμερα από το push.
- Οι agents (developer, QA) ανοίγουν το PR. Τη συγχώνευση την πατά ο ιδιοκτήτης, ή ο agent όταν ο ιδιοκτήτης το ζητήσει ρητά.
- Το «merge = κυκλοφορία» μένει: οι σημειώσεις έκδοσης (`package.json`, `releases.json`, `npm run changelog`) μπαίνουν στο PR **πριν** από το merge.
- Server/migrations: όπως σήμερα, ο ιδιοκτήτης τρέχει `d1 migrations apply --remote` και `npx wrangler deploy` πριν πατήσει merge στο PR της εφαρμογής.
- Tag `vX.Y.Z`: στο commit του merge, μετά το merge.
- Επείγουσα διόρθωση (π.χ. critical έκδοση): κι αυτή μέσα από PR. Τα tests τρέχουν σε ≤ 10′, άρα δεν χρειάζεται παράκαμψη. Αν ο ιδιοκτήτης θέλει δικαίωμα παράκαμψης για τον εαυτό του, αυτό είναι ρύθμιση του ruleset (δες Ανοιχτά ερωτήματα).

Προτεινόμενο κείμενο για την ενότητα «## Git» του `docs/product/WORKFLOW.md` (αντικαθιστά τις κουκκίδες 4–6):

```
- Το `main` αλλάζει **μόνο με Pull Request**. Απευθείας push στο `main` δεν γίνεται (το εμποδίζει το GitHub).
- Ένα PR συγχωνεύεται μόνο όταν είναι πράσινα το «E2E» (Playwright, `.github/workflows/e2e.yml`) και το `npm test`, και το branch είναι ενημερωμένο με το `main`. Πριν ανοίξει το PR τρέχουν τοπικά `npm test`, `npm run typecheck`, `npm run build` και, για αλλαγές οθόνης, `npm run e2e`.
- Το PR της κυκλοφορίας περιέχει ήδη την έκδοση στο `package.json`, την εγγραφή στο `src/releases.json` και το `npm run changelog`. Το merge το πατά ο ιδιοκτήτης (ή ο agent, αν του το ζητήσει ρητά) και ξεκινά το deploy στο GitHub Pages. Αν η έκδοση θέλει νέο server ή migration, πρώτα τρέχει ο χρήστης `d1 migrations apply --remote` και `npx wrangler deploy`, και μετά γίνεται το merge.
- Αν το «E2E» αποτύχει: διόρθωση στο ίδιο branch. Αν είναι ασταθές test, ο qa-tester το βάζει σε καραντίνα με αιτία (όχι παράκαμψη του check).
```

## Ανοιχτά ερωτήματα

1. **Παράκαμψη από τον ιδιοκτήτη:** στο ruleset του `main`, να έχει ο ιδιοκτήτης δικαίωμα «bypass» για επείγουσα περίπτωση, ή καμία εξαίρεση; Πρόταση BA: καμία, αφού τα tests τελειώνουν σε ≤ 10′. Αν μια μέρα το GitHub Actions δεν δουλεύει, η παράκαμψη γίνεται προσωρινά από τις ρυθμίσεις, με εγγραφή στο `DECISIONS.md`.
2. **Ποιος πατά το merge:** μόνο ο ιδιοκτήτης ή και οι agents μετά από ρητή εντολή; Αυτό καθορίζει το κείμενο του `WORKFLOW.md` παραπάνω.
3. **Αποτέλεσμα του spike WebKit:** αν το WebKit του Playwright δεν μπορεί να κάνει κάτι από τις ροές 5–6 (π.χ. εναλλαγή A/B του service worker), δέχεσαι αυτό το κομμάτι ως `test.fixme` συν χειροκίνητη λίστα iPhone, ή να ψάξουμε άλλο δρόμο (π.χ. self-hosted Mac runner, με κόστος);
